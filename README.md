# ShortestPath 프로젝트

## 1. 한 줄 소개

도로 Shapefile을 탐색용 그래프로 전처리하고, 직접 구현한 양방향 가중 A\* 계열 엔진으로 경로·회전 안내·예상 이동시간을 제공하는 Spring Boot GIS 백엔드입니다.

- 프론트 프로젝트 및 영상
[https://github.com/taesooooo/ShortestPath-Front]

## 2. 프로젝트 개요

ShortestPath는 외부 길찾기 API를 호출하는 대신 도로 데이터를 직접 가공하고 경로 탐색 엔진을 구현한 프로젝트입니다. 지도 데이터는 OSM(Open Street Map)을 이용하여 GeoTools로 Shapefile의 선형 도로 데이터를 읽어 노드와 방향성 엣지로 변환하고, 이를 고정 길이 바이너리 파일과 파일 기반 인덱스에 저장합니다. 요청 시에는 출발지와 목적지에서 동시에 탐색해 두 탐색하여 응답합니다.

경로 탐색 외에도 PostgreSQL/PostGIS와 MyBatis를 이용한 음식점 목록, 상세, 키워드, 카테고리, 지도 영역(BBox) 검색 API를 제공합니다.

## 3. 프로젝트에서 어려웠던 점과 해결 과정

### 3.1 원본 도로 데이터를 바로 탐색에 사용할 수 없는 문제

**문제:** Shapefile은 지도 표현용 Geometry 중심이라 중복 좌표, 일방통행, 도로 등급을 그대로 경로 탐색에 사용할 수 없었습니다.

**개선:** 좌표를 정수 키로 변환해 중복을 제거하고, 연속 좌표를 방향성 엣지로 만들었습니다.OSM 데이터에 속성들을 반영해 방향·등급·거리·속도를 저장했습니다.

**결과:** 원본 도로 데이터를 정·역방향 탐색과 도로 등급별 비용 계산이 가능한 바이너리 데이터로 추출 하고 그래프 데이터로 사용할 수 있게 되었습니다.

### 3.2 노드·엣지 추출과 저장이 순차적으로 처리되는 문제

**문제:** 추출과 저장을 순차 처리하면 서로를 기다리고, 변환 결과를 모두 모아두면 메모리 사용량이 증가했습니다.

**개선:** 최대 1,000개 단위 배치와 크기 2,000의 `BlockingQueue`를 두고, 추출 생산자와 4개의 저장 워커를 분리했습니다.

**결과:** Shapefile 읽기와 파일 저장을 병렬화했으며, bounded queue의 back-pressure로 메모리 증가도 제한했습니다.

### 3.3 대용량 엣지 정렬의 메모리와 처리 시간 문제

**문제:** 전체 엣지를 메모리에 올려 정렬하는 방식은 데이터가 커질수록 메모리와 처리 부담이 증가했습니다.

**개선:** 엣지를 50만 개 단위로 나누어 4개 스레드에서 병렬 정렬하고, 임시 청크를 외부 k-way 병합해 정·역방향 파일로 기록했습니다.

**결과:** 전체 데이터를 한 번에 적재하지 않고도 대용량 엣지를 정렬할 수 있어 메모리 사용을 줄일 수 있었습니다.

### 3.4 탐색 속도 문제

**문제:** 맨 처음에는 다익스트라 알고리즘을 이용해 탐색을 했었습니다. 하지만 다익스트라는 현재 노드까지의 누적 거리와 다음 노드의 거리를 더한 값으로만 사용해 최단 경로를 찾지만 목적지 방향을 고려하지 않아 장거리 요청에서 방문 노드와 큐 연산이 증가했습니다.

**개선 과정**

| 단계            | 우선순위 기준                                           | 개선 목적                              | 특징과 한계                                   |
| --------------- | ------------------------------------------------------- | -------------------------------------- | --------------------------------------------- |
| 다익스트라      | 출발지 → 현재 노드의 누적 거리                          | 정확한 최단 경로 기준 구현             | 목적지 방향을 몰라 탐색 범위가 넓어질 수 있음 |
| 단방향 A\*      | 출발지 → 현재 노드의 누적 거리 + 목적지까지의 예상 거리 | 하버사인 휴리스틱으로 목적지 방향 우선 | 불필요한 노드·엣지 방문 감소                  |
| 가중·계층형 A\* | 도로 등급·속도를 반영한 누적 비용 + 목적지 예상 비용    | 주요 도로 선호                         | 순수 최단성보다 서비스 목적을 반영            |
| 양방향 가중 A\* | 각 방향의 누적 비용 + 반대편 종점까지의 예상 비용       | 양쪽에서 중간 지점까지 탐색            | 역방향 그래프와 만남 조건 필요                |

**결과:** A\*로 목적지 반대 방향의 방문과 큐 연산을 줄였고, 양방향 탐색으로 탐색 깊이까지 줄여 다익스트라 방식보다 탐색 속도를 개선했습니다.

기존 다익스트라를 사용했을때 장거리 기준 15초 정도에서 A\*를 사용하여 최소 3~5초까지 줄일 수 있었습니다.

### 3.7 대용량 지도 데이터를 메모리에 올릴 수 없는 문제

**문제:** 대용량 노드·엣지 데이터를 모두 Java Heap에 적재하면 메모리 사용량이 지나치게 커져 전체 데이터를 안정적으로 사용할 수 없었습니다.

**개선:** 노드와 엣지를 고정 길이 바이너리 파일로 저장하고, `MappedByteBuffer`로 파일을 메모리에 매핑해 필요한 구간과 필드만 직접 읽도록 구현했습니다.

**결과:** 전체 데이터를 Heap에 올리지 않고도 운영체제의 가상 메모리를 통해 대용량 그래프 데이터에 접근하여 경로 탐색에 사용할 수 있게 되었습니다.

### 3.8 탐색마다 큰 상태 배열을 생성하고 초기화하는 문제

**문제:** 탐색 상태 배열을 전체 노드 크기로 생성·초기화하면 요청마다 메모리 할당과 GC 부담이 발생합니다.

**개선:** 실제 탐색 노드에 local index를 부여하고 사용한 매핑만 초기화했습니다. 탐색 상태 배열은 Pool로 관리해 재사용했습니다.

**결과:** 요청마다 큰 배열을 반복 생성하지 않아 메모리 할당과 GC 비용을 줄였습니다.

## 4. API 요약

### 경로 API

| Method | URL                                                                            | 설명                                                                      |
| ------ | ------------------------------------------------------------------------------ | ------------------------------------------------------------------------- |
| `GET`  | `/api/map/find-path?coordinates=출발위도/출발경도\|도착위도/도착경도`          | 하나 이상의 좌표 쌍에 대한 경로, 회전 안내, 탐색 시간, 예상 이동시간 반환 |
| `GET`  | `/api/map/search-route-track?coordinates=출발위도/출발경도\|도착위도/도착경도` | 단일 경로 결과와 양방향 탐색 과정 반환                                    |

`find-path`의 핵심 응답 필드는 `start`, `end`, `routeSteps`, `searchTime`, `estimatedTravelTimeSeconds`입니다.

### 음식점 API

| Method | URL                                    | 설명                               |
| ------ | -------------------------------------- | ---------------------------------- |
| `GET`  | `/api/restaurants`                     | 음식점 목록과 페이징 정보 조회     |
| `GET`  | `/api/restaurants/{id}`                | 음식점 상세 조회                   |
| `GET`  | `/api/restaurants/category/{category}` | 업종 카테고리와 선택적 키워드 검색 |
| `GET`  | `/api/restaurants/search`              | 키워드·카테고리·BBox 통합 검색     |

목록 API는 `page`, `size` 파라미터를 `PageInfoArgumentResolver`에서 공통 처리합니다.

## 6. 테스트 전략

Gradle에서 단위 테스트와 통합 테스트 소스셋을 분리했습니다.

- `src/test`: 경로 엔진, 탐색 버퍼, 회전 안내, 추출기, 정렬, 파일 저장소, 인덱스, 서비스 단위 테스트
- `src/integrationTest`: 실제 Shapefile 전처리, 엔진 경로 연결성, MyBatis Mapper, Controller 요청 흐름 테스트
- 파일 테스트는 임시 디렉터리를 사용해 테스트 간 데이터를 격리합니다.
- 엔진 테스트는 경로 존재 여부만 보지 않고 인접 노드 사이에 실제 엣지가 있는지, 정방향·역방향 결과가 연결되는지 검증합니다.
